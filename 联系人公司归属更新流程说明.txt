联系人公司归属更新流程说明（update-company）
============================================

本说明只解释 crm.py 中 update-company 子命令的既有行为，不提出、
也不新增任何功能。文中所有结论均依据实际读取的仓库文件，引用格式
为"相对路径:行号"：

  - crm.py（命令行入口与全部业务逻辑，共 248 行）
  - tests/test_update_company.py（update-company 的子进程回归测试，
    共 239 行）

add 与 list 在本说明中只作为准备数据和核对结果的手段出现，其自身
行为不在本文展开。文中样例的输出均为依据源码逐行推导的"预期结果"，
未标注为实测；id 等由 SQLite 分配的值只在"全新数据库、按序插入"
这一前提下成立，换用已有数据库时以当次 add 输出为准。

不改动范围：本文不修改 crm.py、tests/ 下任何测试、README.md，
也不改动数据库表结构；add、list、update-email 的公开行为保持原样，
本文对它们的引用仅为说明 update-company 的上下文。


一、命令入口与参数
------------------

update-company 子命令在 build_parser() 中注册（crm.py:230-235）：

    python crm.py --db <数据库文件> update-company --id <联系人编号> --company <新公司名>

  - --db 是顶层解析器的必填参数（crm.py:210，required=True），
    必须写在子命令之前；没有默认存储位置。
  - 子命令 update-company 的处理函数是 cmd_update_company
    （crm.py:235 的 set_defaults，函数体在 crm.py:160-168）。
  - --id 与 --company 均为 required=True（crm.py:233-234），
    除"必填"外没有缺省值或可选参数；漏传由 argparse 拒绝，
    退出码 2，用法文本由 argparse 生成。
  - 解析与分派发生在 main()（crm.py:240-243）。

cmd_update_company 本身不直接写逻辑，而是调用两个更新入口共用的
update_contact_field()（crm.py:113-146），并传入本命令专属的四个
参数（crm.py:161-168）：字段名 "company"、原始输入 args.company、
校验函数 bool、错误消息 "must not be empty"，以及更新语句
"UPDATE contacts SET company = ? WHERE id = ?"。因此 update-company
的校验顺序、数据库访问规则与输出形态和 update-email 完全一致，
差别只在目标字段与校验规则。


二、一次更新的完整路径：输入 → 校验 → 提交 → 输出
-------------------------------------------------

按 update_contact_field()（crm.py:113-146）的执行顺序：

1. 编号清理与校验（crm.py:120 调用 parse_contact_id，crm.py:44-53）
   先将 --id 的原始字符串经 clean()（crm.py:39-41，即
   value.strip()）去掉首尾空白，再校验：
     - 清理后非空；
     - 每个字符都是数字 0-9（允许前导零，如 "001"）；
     - 整数值落在 1 到 9223372036854775807（MAX_CONTACT_ID，
       crm.py:30）之间。
   任一不满足即 fail("id", "must be a positive integer")。
   通过后 int(raw_id) 得到整数编号，前导零随之消去。

2. 公司名清理与校验（crm.py:121-123）
   新公司名同样经 clean() 去首尾空白；update-company 的校验函数
   是 bool（crm.py:165），即清理后为空字符串（纯空白或空串）时
   fail("company", "must not be empty")。除"非空"外没有其他
   公司名规则。
   注意顺序：编号校验在公司校验之前，两者同时无效时只报告编号
   错误（tests/test_update_company.py:32-34 的用例固定了这一点）。

   fail()（crm.py:33-36）把"<字段>: <消息>"一行写入标准错误，
   标准输出保持为空，然后 sys.exit(2)。以上两步校验全部发生在
   打开数据库之前（crm.py:120-123 在 crm.py:125 的 connect_db
   之前），所以输入校验失败时进程根本不触碰数据库文件。

3. 打开数据库（crm.py:125 调用 connect_db，crm.py:71-78）
   - 先用 Path(db_path).parent.is_dir() 检查父目录；父目录不存在
     时 fail("db", "parent directory does not exist")，程序不会
     代为创建目录或文件。
   - 父目录存在时 sqlite3.connect(db_path)：文件不存在则新建，
     已存在则原样复用；随后执行 CREATE TABLE IF NOT EXISTS
     contacts（CREATE_TABLE_SQL，crm.py:20-27）并 commit。
     表结构为 id INTEGER PRIMARY KEY AUTOINCREMENT、
     name/email/company 三个 TEXT NOT NULL 列。

4. 核对联系人存在并提交更新（crm.py:126-136）
   - 先 SELECT id, name, email, company FROM contacts WHERE id = ?
     （crm.py:127-130）；查无此行时
     fail("id", "contact not found")，不执行任何 UPDATE。
   - 存在时执行 UPDATE contacts SET company = ? WHERE id = ?
     （crm.py:133，语句来自 crm.py:167），绑定的是 clean 之后的
     公司名与整数编号，随后 conn.commit()，并在 finally 中
     conn.close()。即：修改在进程结束前已提交落盘。
   - 该 UPDATE 只触及 company 一列、只命中 id 匹配的一行；
     name、email 与其他联系人的行不会被这条语句修改。

5. 输出（crm.py:138-146）
   用第 4 步 SELECT 读回的行组装含 id/name/email/company 四个键
   的对象，再把 company 键覆盖为 clean 后的新公司名
   （crm.py:144），json.dumps(..., ensure_ascii=False) 输出单行
   JSON 到标准输出，中文不转义，返回退出码 0。因此输出中编号、
   姓名、邮箱是更新前的原值（本就不被修改），公司是清理后的新值。

company 字段的真实含义：company 只是 contacts 表行内的一个自由
文本列（crm.py:25），仓库中不存在独立的"公司"表或公司主数据。
因此 update-company 只是把该联系人行内的这段文本改写为新值：
不会创建任何"公司档案"，也不会把同公司的其他联系人一并迁移——
把林宁改到远帆咨询后，许禾仍留在星河科技，除非再对她单独执行
一次 update-company。同理，新公司名不需要事先存在，旧公司名也不
会因最后一名联系人离开而被"删除"。


三、样例：完整成功路径（预期结果）
----------------------------------

前提：工作目录为 crm.py 所在目录，使用父目录已存在的全新数据库
contacts.sqlite3（执行前文件不存在）。id 1/2/3 依赖"全新库 + 按此
顺序插入"这一前提（id 由 SQLite AUTOINCREMENT 分配，crm.py:22）。

1) 准备数据（三条 add，各自独立进程）

     python crm.py --db contacts.sqlite3 add --name 林宁 --email lin@example.test --company 星河科技
     python crm.py --db contacts.sqlite3 add --name 许禾 --email xu@example.test --company 星河科技
     python crm.py --db contacts.sqlite3 add --name 周岚 --email zhou@example.test --company 远帆咨询

   预期标准输出（退出码均为 0）：
     {"id": 1, "name": "林宁", "email": "lin@example.test", "company": "星河科技"}
     {"id": 2, "name": "许禾", "email": "xu@example.test", "company": "星河科技"}
     {"id": 3, "name": "周岚", "email": "zhou@example.test", "company": "远帆咨询"}

   这组准备数据与 tests/test_update_company.py:86-102 的
   seed_update_company_contacts() 完全一致。

2) 更新林宁的公司归属（编号与公司都带首尾空白，编号带前导零）

     python crm.py --db contacts.sqlite3 update-company --id " 001 " --company " 远帆咨询 "

   预期标准输出（退出码 0，标准错误为空）：
     {"id": 1, "name": "林宁", "email": "lin@example.test", "company": "远帆咨询"}

   说明：编号 " 001 " 经 clean 与 int 归一为 1；公司 " 远帆咨询 "
   去除首尾空白后写入；编号、姓名、邮箱保持原值（对应第二节第 5
   步的输出组装）。tests/test_update_company.py:122-157 的
   test_update_company_success_persists_and_moves_contact 用同样
   带空白和前导零的输入覆盖了这一路径。

3) 重新查询两家公司（独立命令，验证已提交的修改）

     python crm.py --db contacts.sqlite3 list --company 星河科技

   预期标准输出（只剩许禾）：
     [{"id": 2, "name": "许禾", "email": "xu@example.test", "company": "星河科技"}]

     python crm.py --db contacts.sqlite3 list --company 远帆咨询

   预期标准输出（按编号升序：林宁、周岚）：
     [{"id": 1, "name": "林宁", "email": "lin@example.test", "company": "远帆咨询"}, {"id": 3, "name": "周岚", "email": "zhou@example.test", "company": "远帆咨询"}]

   为何重新查询能读到已提交结果：每条命令都是独立的 Python 进程；
   update-company 在 close 前已 conn.commit()（crm.py:134-135），
   修改随事务提交写入同一个 SQLite 文件；后续 list 进程用同一
   --db 路径重新 connect（crm.py:182），执行
   SELECT ... WHERE company = ? ORDER BY id ASC（crm.py:185-189）
   即可读到已提交数据。跨进程可见的依据就是"提交到同一文件 +
   后续重新打开该文件"，与进程内缓存无关。

4) 再次提交相同公司（幂等成功，不产生新记录）

     python crm.py --db contacts.sqlite3 update-company --id 1 --company 远帆咨询

   预期标准输出（退出码 0，与第 2 步相同）：
     {"id": 1, "name": "林宁", "email": "lin@example.test", "company": "远帆咨询"}

   UPDATE 把 company 写成相同值仍按成功处理；随后再查两家公司，
   星河科技 1 条（许禾）、远帆咨询 2 条（林宁、周岚），总记录数
   保持三条，所有记录内容不变。
   tests/test_update_company.py:159-176 的
   test_update_company_same_value_again_still_succeeds_without_new_records
   固定了这一行为。


四、失败分支（预期结果）
------------------------

以下失败有共同形态（tests/test_update_company.py:114-120 的
assert_update_rejected 逐条断言）：退出码为 2；标准输出为空；
标准错误恰好是对应的一行（带行尾换行），没有 Python 异常堆栈。
错误由 fail()（crm.py:33-36）产生。

1) 编号不是正整数

     python crm.py --db contacts.sqlite3 update-company --id 0 --company 远帆咨询
     python crm.py --db contacts.sqlite3 update-company --id 1.5 --company 远帆咨询

   预期标准错误（两种输入相同）：
     id: must be a positive integer

   依据 parse_contact_id（crm.py:44-53）：0 不在 1 到上限之间，
   1.5 含非数字字符。空白编号、超出 64 位有符号整数上限的编号
   同样报这一行，见 tests/test_update_company.py:19-27 的
   INVALID_UPDATE_COMPANY_CASES。

2) 合法编号配空白公司

     python crm.py --db contacts.sqlite3 update-company --id 1 --company "   "

   预期标准错误：
     company: must not be empty

   依据 crm.py:121-123：clean 后为空即拒绝（空串、纯空格、
   含制表符的空白等价，见 tests/test_update_company.py:29-31）。

3) 编号与公司同时无效

     python crm.py --db contacts.sqlite3 update-company --id 1.5 --company "   "

   预期标准错误（只报告编号，不报告公司）：
     id: must be a positive integer

   依据校验顺序：parse_contact_id（crm.py:120）在公司校验
   （crm.py:121-123）之前，编号失败即退出。用例见
   tests/test_update_company.py:32-34。

4) 输入合法但编号不存在

     python crm.py --db contacts.sqlite3 update-company --id 99 --company 远帆咨询

   预期标准错误：
     id: contact not found

   依据 crm.py:127-132：SELECT 查无此行即拒绝，不执行 UPDATE。
   tests/test_update_company.py:203-212 用"最大 id + 1000"和
   上限值 9223372036854775807 两个不存在的编号覆盖此分支。

5) 输入合法但 --db 父目录不存在

     python crm.py --db no-such-dir/contacts.sqlite3 update-company --id 1 --company 远帆咨询

   预期标准错误：
     db: parent directory does not exist

   依据 connect_db（crm.py:73-74）。程序不会自动创建缺失的目录，
   也不会创建数据库文件；tests/test_update_company.py:226-234
   断言执行后目录与文件都不存在。


五、失败对数据库的影响：三种情形要分清
--------------------------------------

1) 输入校验失败（编号或公司不合法）：校验在 connect_db 之前
   （crm.py:120-123 对比 crm.py:125），进程根本不打开数据库。
   指向已有库时，库内记录逐字段不变；指向尚不存在的新文件时，
   该文件（及任何 SQLite 伴随文件）不会被创建。
   对应测试：tests/test_update_company.py:178-188
   （已有记录不变）与 tests/test_update_company.py:190-201
   （新文件不被创建）。

2) 输入合法、编号不存在、数据库原本不存在但父目录存在：此时
   connect_db 会先创建空数据库文件并建表（crm.py:75-77），随后
   SELECT 查无记录，才报告 id: contact not found。即"合法输入 +
   未知编号"会先留下一个空数据库再报错；随后对该库执行
   list --company 远帆咨询 得到 []（退出码 0）。
   对应测试：tests/test_update_company.py:214-224。

3) 输入合法、编号不存在、数据库已存在：不写入任何内容，已有记录
   逐字段不变（tests/test_update_company.py:203-212 在每次拒绝后
   重新 list 两家公司核对）。

4) 父目录缺失：在 connect_db 入口处即被拒绝（crm.py:73-74），
   不创建目录、不创建文件，与第 2 种情形（父目录存在时创建空库）
   形成对照。对应测试：tests/test_update_company.py:226-234。


六、行为边界（如实记录，不作推测）
----------------------------------

  - update-company 只改 company 一列、只改 id 匹配的一行；不存在
    "公司改名联动""批量迁移同公司联系人""公司档案管理"等行为，
    依据是更新语句仅 UPDATE contacts SET company = ? WHERE id = ?
    （crm.py:167）且全仓库无公司主数据表。
  - 重复提交相同公司按成功处理，记录数不变（见第三节第 4 步）。
  - 多进程并发写同一数据库、数据库文件被外部改写或损坏后的表现，
    已读材料中没有依据，本文不作结论。
  - 本文未实际修改任何仓库文件；add、list、update-email 的公开
    行为与数据库表结构保持原样。
